# Relay 产品升级方向

依据：2026-10-11 当前源码与已有功能。第一阶段已在 0.1.14 实施，操作和边界见 [请求检查与变量链路](request-checks.md)。0.1.15新增本地AI连接、通用skill和真实验证到交付的链路；文档批量验证已通过API开放。契约漂移检测、计划关联验证和第三阶段增强仍是方案。竞品近期版本、套餐和限制未逐项实测，因此不作“竞品都没有”的判断。

## 产品主线

面向承担接口联调和交付的开发者：请求跑通后形成带执行证据的交付稿，再持续检查实现是否偏离已确认的约定。个人开发者的轻量调试体验作为基础入口。

当前已具备 cURL 草稿、关联请求、变量解析、执行快照、字段推导、验证过期提示和多格式导出。应围绕这条链路升级，不需要先推翻整套工作台。

## 当前能力与需要纠正的判断

| 判断 | 当前实现 | 升级方向 |
| --- | --- | --- |
| 运行计划“通过”只看请求成功 | 0.1.14 已加入状态码、JSON 字段和耗时检查、运行变量提取 | 下一阶段把执行证据与文档持续验证关联 |
| Cookie 能力缺失 | 已有共享 Cookie Jar 与启用开关 | 增加域名维度的查看、编辑、清除及有效期展示 |
| 文档不会过时 | 配置或环境变化会提示重新验证；未主动检测远端变化 | 保存确认基线，重新运行后显示契约差异；失败不覆盖已确认基线 |
| 响应样例可以生成完整契约 | 样例能推导观察到的结构，无法证明业务语义、必填和所有变体 | 必填、可空、枚举与兼容性由开发者确认，自动结果明确标为推导 |
| 安装包小就是独有卖点 | 使用系统 WebView2，安装包小；运行时占用另计 | 宣传可测量的安装体积、启动与本地工作流，避免未经测量的倍数比较 |

## 第一阶段：让检查结果可信

1. 每个请求添加表单式检查：允许的状态码、JSON 路径存在/相等/类型、响应耗时上限。错误响应也可作为预期，例如 401 用于验证鉴权拒绝。
2. 响应字段可提取到本次运行变量，例如登录获取 token，再调用业务接口。默认只在本次计划生效；提取失败不得沿用旧值；写回环境需明确选择。
3. 结果弹窗列出每项规则的预期、实际和失败位置，与当次请求/响应快照关联。取消、跳过、网络失败与检查失败分别显示。
4. 增加 OpenAPI 3 与 HAR 的本地导入预览：选择请求、排除敏感头、提示不支持项。外部集合工具的导入入口继续遵循当前产品取舍，不作为本阶段任务。

验收流程：登录 → 提取 token → 创建资源 → 查询 → 检查字段 → 清理资源。HTTP 200 但业务字段不符时，应判为检查失败，定位到字段。

## 第二阶段：交付文档的持续验证

1. 文档统一展示“未验证 / 已验证 / 需重新验证 / 有差异 / 执行失败”。验证时间、环境和基线版本可查询。
2. 支持运行选中接口或批量验证。默认选取声明为只读的接口；写入接口单独选择，明确环境、执行顺序、取消与失败策略。
3. 新样例与确认基线比较：字段新增、删除、类型变化、可空变化。空数组、异构数组和可选字段提示证据不足，不把一次未出现当作必然删除。
4. 差异确认后更新基线，保留原字段说明与历史证据；检查失败不会悄悄覆盖交付版本。
5. 文档可关联运行计划，应用开启期间周期验证；展示最后执行与下次执行，避免暗示关闭应用仍在监控。

演示目标：粘贴 cURL → 执行 → 补充说明 → 确认交付 → 服务字段改变 → 重新验证 → 定位差异。建议对外表述“带执行证据的接口文档”，避免保证文档永远正确。

## 第三阶段：增强个人调试入口

- 流式阅读：保留事件原文，同时拼接增量文本、工具调用参数和完成原因；支持常见协议适配与自定义映射。
- 指标：区分首字节、首事件和首个有效文本片段时间。只有服务端提供真实 usage 或选定 tokenizer 后才显示 token 速率；不能将事件数当 token 数。
- 响应对比：比较两次运行或不同环境，支持忽略时间戳/traceId、按键匹配数组、结构与值分别查看。
- 项目目录：请求与文档采用稳定标识的文本文件；凭据、运行历史与个人设置单独存储。明确外部改动、并发写入、冲突与迁移规则。
- OAuth2：按目标用户的接口需求优先支持客户端凭证、授权码 + PKCE，再评估刷新令牌管理。

## 体验原则与验证

粘贴命令后立即展示可编辑的请求预览，按 Ctrl+Enter 执行；粘贴本身不自动发送。响应 JSON 树允许复制路径和提取变量，数组表格作为可切换视图。网络阶段瀑布图只有在引擎有真实测量时展示，连接复用、代理与 HTTP/2 单独考虑，不估算 DNS/TCP/TLS。

视觉升级以具体任务为单位：请求页帮助定位配置，响应页帮助找到错误，文档页表达交付状态。通过六套配色的明暗截图、最小窗口与字号检查验证，避免继续全局更改圆角或装饰性发光。

推进前先用同一真实联调任务检查候选方案：首次成功响应所需时间、配置 token 链路的步骤数、定位业务失败的时间，以及发现文档差异所需操作。竞争力以这些任务结果和用户试用反馈判断。

## 已落地的AI工作流

本地认证API让AI创建接口、检查规则与说明，执行HTTP验证并补写交付字段。工作区仍由应用内的同一状态与保存流程管理；更新检查版本和未保存草稿。用户在Relay中审阅并确认交付，AI不能伪造验证证据或标记已审核。操作见[AI工作流](ai-workflow.md)。
