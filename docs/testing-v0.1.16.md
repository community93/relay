## 这一版新增的验证

MCP 与 `/v1/command` 共用同一个端口、同一份凭证、同一套能力分级，所以边界检查在两条路径上各做一遍，而不是假设它们一致：

- `initialize` 回报协议版本、服务名与当前权限；客户端要求一个 Relay 不实现的版本时回落到最新实现版本，而不是原样回声。
- `tools/list` 在可执行连接下给出全部 15 个工具，且工具名不含点；只读连接只给出 `entity_get`、`job_get`、`workspace_list` 三个，内部的 `mcp_tools` 从不出现在列表里。
- 跳过 `tools/list` 直接 `tools/call` 一个越权工具，返回的是带 `isError` 的工具结果并写明该申请哪一档，不是传输错误——模型能在对话里读到它并去问用户。
- 未知工具返回 `-32602`，未知方法返回 `-32601`，未认证返回 401，通知（无 `id`）返回 202 且没有响应体。
- MCP 路径同样受主机白名单约束：白名单只有 `127.0.0.1` 时执行指向 `api.off-list.test` 的请求被拦下。

跳转逐跳校验用 `127.0.0.1 → localhost` 这对同机不同名做验证，不需要外网：

- 白名单只有 `127.0.0.1` 时，指向 `/redirect-cross` 的执行停在半路，报错写明「重定向目标是未授权主机 localhost」，`errorKind` 为 `redirect`。此前 reqwest 只会给出固定文案「error following redirect」，用户看不出是被谁拦下的。
- 白名单补上 `localhost` 后同一请求正常跟随到 `http://localhost:8899/hello`。
- 应用内手动点**发送**（空白名单）不受这条限制，仍然正常跟随——限制只作用于 AI 连接驱动的执行。
- Rust 侧另有一个真实套接字用例：进程内起一个会 302 到另一主机名的服务器，直接断言被钉住的客户端拒绝、覆盖到的客户端与 unrestricted 客户端放行。

## 范围

自动验证当前支持 HTTP。SSE/WS 可创建配置并在工作台中调试；MCP 只提供工具调用，不推送事件流（`GET /mcp` 返回 405，任务进度轮询 `job_get`）；没有任意脚本执行、文档契约漂移检测或关闭应用后的后台运行。识别到的凭据会脱敏，仍需在外发前审核业务说明和自由文本。

操作步骤见 [AI 工作流](ai-workflow.md)，命令结构见 [API 参考](../skills/relay-workflow/references/api.md)。
